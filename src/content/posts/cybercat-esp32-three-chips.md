我想做一个叫「赛博猫猫」的东西：能听唤醒词、能接云端转写、能聊天、能播歌、能控家电。

听起来像把几个现成库拼一拼。实际上，真正卡住我的不是功能，是**一颗芯片装不下这么多东西**。

## 为什么不是一颗芯片

最开始的想法很直接：一块 ESP32-S3，麦克风、喇叭、蓝牙、红外都接上，一个固件全包。

卡在第一个事实：**ESP32-S3 没有蓝牙经典（Bluetooth Classic）**，它只有 BLE。而要让家里的蓝牙音箱出声，得用 **A2DP**，那是经典蓝牙的东西。

所以「拿 S3 当蓝牙音源」这条路从一开始就不存在。

于是变成三颗：

| 芯片 | 职责 | 为什么是它 |
|---|---|---|
| **ESP32-S3** N16R8 | 唤醒词、命令识别、云端 ASR、对话、TTS、ESP-NOW、闹钟 | PSRAM 够大，跑得动 ESP-SR 模型 |
| **ESP32-WROOM-32** | TF 卡音乐、PCM 重采样、Bluetooth A2DP Source | 只有它有经典蓝牙，能当音源 |
| **ESP32-C3** | 红外学习与发射、NVS 保存 | 功耗低，可以一直开着等命令 |

S3 和 WROOM 之间用 UART 硬连（921600、8N1），S3 和 C3 之间走 ESP-NOW（无线，省一根线）。

接线就三根线的事：

```
S3 GPIO17 TX → WROOM GPIO16 RX
S3 GPIO18 RX ← WROOM GPIO17 TX
GND ↔ GND
```

两颗都是 3.3 V GPIO，不用电平转换，但**必须共地**。

## 第一个坑：320 KB 压根不够用

三颗芯片定下来，我以为剩下的就是写代码。直到我把 WROOM 的启动日志打出来：

| 阶段 | 剩余堆 |
|---|---:|
| `setup()` 开始 | 189,792 B |
| SPIFFS 挂载 | 185,332 B |
| TF 卡挂载 | 142,620 B |
| **蓝牙启动** | **48,912 B** |

蓝牙一开，93.7 KB 没了，只剩 49 KB。

而当时的设计是：TTS 音频在 S3 上生成成 MP3，传给 WROOM 存到 TF 卡，再用 libmad 解码放出去。

libmad 要 **29,192 B，而且必须是一整块连续内存**（单一个 `mad_frame` 就 20,784 B）。剩 19 KB 给整个蓝牙栈的结果：

```
解码器初始化失败：free=19372 largest=18420
```

`largest` 比 `free` 小，说明内存不是不够，是**碎了**。

那预先留出 29 KB 呢？蓝牙建链时分配失败，直接走到清理路径里的断言：

```
assert failed: vQueueDelete
```

## 换个更小的解码器也不行

自然想到换 minimp3。它确实更小，但算上 scratch 反而更大：

```
scratch 16 KB + 解码器 6.6 KB + 缓冲 ≈ 31.6 KB
```

而且那 16 KB scratch 放不进任何一个任务的栈，实测栈溢出。

结论写在了文档里：

> 这块板子无法同时容纳「Bluedroid + 30 KB 级 MP3 解码器 + TF 挂载」。

## 转折：不让它解码

既然 WROOM 没余力解码，那就**别在 WROOM 上解码**。

现在的链路是：

1. S3 向云端 TTS 要 **WAV**（实测返回 24 kHz / 16 bit / 单声道）
2. S3 解析 RIFF，把 PCM 按块通过 UART 下发
3. WROOM 不做解码，只把 24 kHz 重采样到 44.1 kHz，直接推 A2DP

顺带一个坑：请求 `format=pcm` 不被支持，服务端会默默回落成 MP3，所以得主动要 WAV 再自己拆头。

波特率也得改：24 kHz 单声道的 PCM 是 384 kbps，原来的 230400 不够，回到 921600。

libmad 没删，但只留给 TF 卡本地文件用，按需分配，分配失败就回 `ERR:MP3_NO_MEMORY`——宁可报错，也不假装能放。

## 然后是六个时序坑

链路通了不等于能听。这些是一个一个撞出来的：

| 问题 | 现象 | 处理 |
|---|---|---|
| 桥端靠轮询取数 | 1031 字节一帧要 29 ms（线速应该 12 ms） | 改用阻塞读 `uart_read_bytes`，降到 10–13 ms |
| S3 逐块停等 | 1 KB / 130 ms，只有 25 KB/s | 改滑动窗口 + 每块确认 |
| 超时取整成 0 | `pdMS_TO_TICKS(2)` 在 100 Hz tick 下等于 0，接收任务变成轮询，触发看门狗并饿死 TTS | 改成 `pdMS_TO_TICKS(10)` |
| 音频路径上打日志 | 主机读串口慢时 `ESP_LOGI` 阻塞 137 ms，ACK 处理卡死，整句 2 秒超时 | 音频路径不再写任何日志 |
| 单块出错整句失败 | 一次 CRC 错误或环满就中断 | CRC 错只重发该块，确认超时只重发该块，环满只丢该块 |
| 无音箱时报错模糊 | 中途丢出一句 `ERR:PCM_NOT_STARTED` | 改成明确的 `ERR:PCM_NO_BT` |

改完之后自测：**409600 字节 / 4826 ms = 84.9 KB/s**（约 850 kbps，符合 921600 的设定）。

跑通那一轮的记录是：

```
收 106 帧 / 108000 字节
推 A2DP 396900
A2DP 取走 396900（844 次），队列排空
```

## 剩下的问题不在固件里

数字都很好看，但同一版固件、同一只音箱，多次实测的取数速率是这样的：

| 轮次 | 桥端 A2DP 请求速率 | 结果 |
|---|---:|---|
| 第 4 轮 | 184 KB/s | 实时，正常 |
| 第 15 轮 | 93 KB/s | 接近实时，能听 |
| 第 21 轮 | 24 KB/s | 严重缺口，只能丢块 |

44.1 kHz 立体声需要 176 KB/s。而设备间 RSSI 一直在 -60 到 -67 dBm 的偏弱区间。

所以这已经不是我代码的问题了：**音频通路的数字部分已经打通，卡在蓝牙射频链路和音箱自己的取数行为上**。下一步是把音箱挪近一点，或者换一只再测。

## 我不打算吹的部分

这个工程有一份单独的「验证记录」，里面明写着哪些是编译通过、哪些只是「应该能行」：

- S3 主体固件在我当时的电脑上**根本没编过**——缺 ESP-IDF 5.4 和约 150 MB 的 ESP-SR 模型组件
- WakeNet / MultiNet 模型必须先 `menuconfig` 选好，再完整 `idf.py flash` 把 `srmodels.bin` 写进去
- 数字麦克风的 I2S 引脚、左右声道、采样位移，得看你手上那块模块，必须上板测波形
- 蓝牙配对、A2DP 连续播放、TF 卡信号、921600 长线稳定性、红外驱动、不同空调的 raw 帧，全部待上板
- 云端 ASR 和对话需要真密钥、可达网络和配额，**不能离线模拟成「已成功」**

这些在文档里都标成「需要额外配置」，没有任何一条写成「已完成」。

## 一句总结

本来以为是「把几个库拼起来」，实际做下来发现是一道 **内存预算题**：

> 蓝牙一开，你只剩 49 KB。所有设计都得围着这个数字转。

接下来想把蓝牙那段的不确定性收敛下来，再看能不能把三块板的固件升级做成一条命令。
